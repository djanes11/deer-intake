# Final project readiness review — September 11, 2026

Follow-up: these seven findings now have local fixes. See `docs/final-readiness-fixes-2026-09-11.md` for validation and the required migration/deployment order. The findings below preserve the original review evidence.

Reviewed the current checkout after the opening-weekend fixes, across intake and order editing, processing/status updates, payments, staff access, printing, reports, and database safeguards. The remaining findings below are based on source tracing; they were not exercised against production. No application code, production payment settings, or customer records were changed during this review.

Validation: `npm.cmd run test:smoke` passed all nine suites; `npm.cmd run build` passed compilation, TypeScript, and static page generation. These checks do not cover every complete browser workflow. Usable server database credentials were not available locally, so the deployed migration and live behavior could not be independently verified.

1. **P1 — Editing an existing order can keep the old charge.** `lib/jobsSupabase.ts:2528` prefers existing `priceProcessing`, `priceSpecialty`, and `price` over newly computed charges. `app/intake/page.tsx:1098` spreads the loaded job into the save payload without replacing these price snapshots with the newly displayed totals. For example, changing an existing order from a cheaper process to a more expensive one can save the new process while retaining the old amount owed. Recompute affected charges on order edits, preserve intentional overrides and unchanged historical prices, and derive the total from the resulting components. Verify process changes, add-ons, specialty quantity changes/removal, and overrides through the actual save path.

2. **P1 — Removing processor membership does not reliably revoke read/print access.** `lib/staffPermissions.ts:21` grants view and print regardless of role. A valid Supabase user without active membership passes `requireStaffAccess`; `getStaffProcessorContext` then falls back to a default processor with `role: null`. The jobs GET endpoint uses this permission check before returning records. Require an authorized processor membership and a resolved processor for these operations, with deliberate handling of platform administrators. Verify that a still-valid account whose membership was removed or deactivated receives a denial from job, report, and print endpoints.

3. **P1 before production Square — Existing sandbox checkout URLs can be reused after switching environments.** `app/api/square/create-processing-payment-link/route.ts:83` finds an active link by job and amounts without checking `square_environment`. Switching configuration to production therefore still returns a matching sandbox URL. Make link reuse environment-aware and retire incompatible links before creating replacements; account for the active-link uniqueness constraint. Verify a sandbox link followed by a production-mode request for the same job and amount.

4. **P1 before production Square — A payment collected during link creation can leave a stale payable checkout.** In `app/api/square/create-processing-payment-link/route.ts:122`, the remote checkout is created after reading the balance, and the local link is inserted afterward without validating that balance again. If staff records payment during that interval, the guarded save cannot supersede a link that has not been inserted yet. The request can then return a checkout for the earlier, larger balance. Reserve/validate checkout creation against the job's payment state, handle concurrent changes before publishing the URL, and reconcile or cancel obsolete remote checkouts. Verify with a delayed Square response and a staff payment between the initial read and local insert.

5. **P2 — Email-login sessions expire in API requests despite browser refresh.** `app/api/staff/session/route.ts:54` copies the access token into an HttpOnly cookie. Browser Supabase auto-refresh is enabled in `lib/supabaseBrowser.ts`, but ordinary staff pages do not synchronize refreshed tokens into that cookie; the only auth-state subscription is on the password-reset page. API requests rely on cookies, and the server rejects the original token after it expires. The cookie's fourteen-day lifetime does not extend the token lifetime. Add shared session refresh handling and verify an email-authenticated shift across token expiry. This finding does not apply to the separate local-username session mechanism.

6. **P2 — Printing makes the open intake's version stale.** `app/intake/page.tsx:1448` marks a job printed but leaves its loaded `updatedAt` unchanged. `lib/jobsSupabase.ts:3201` updates the job, and the new guarded-save path rejects that old version on the next edit. Save → print → edit → save can therefore produce a false “changed by another station” conflict. This is a regression exposed by the recent concurrency protection. Reconcile printing with edit versions without masking another station's concurrent changes; do not simply disable conflict detection. Verify the complete sequence, including a concurrent external edit.

7. **P2 — Cancelling printing still removes sheets from the print queue.** `app/reports/print-queue/page.tsx:156` records the sheet as printed and removes it from the queue before opening print preview. Batch printing does the same. Cancelling the dialog or experiencing a printer failure therefore leaves the record marked printed. Add an explicit completion/retry workflow so unsuccessful prints remain recoverable. A browser print-dialog close event alone does not establish that a physical sheet printed.

I recommend resolving these findings before opening weekend, particularly the pricing and membership issues, and the Square findings before accepting real payments. The passing checks remain useful evidence for the safeguards already added, but are not a complete launch sign-off.

The requested Square production transition and season database preparation remain subsequent planning tasks. No payment environment switch or database clearing was performed. The reset plan should identify exactly which test/season records to remove and which accounts, settings, catalogs, and configuration to preserve before any destructive action is proposed.
